# EveJS RPG Launcher

Локальная ветка `rpg` форка `klimesrenz/evejs-launcher`, версия 0.1.1.
Основа: upstream 1.0.69, commit fdde2ddf80a11237ad0cbd7955ee493d90ff6158.
Исходные лицензия GPL-3.0, авторство и THIRD_PARTY_NOTICES сохранены.

## Версии

`VERSION=1.0.69` — версия исходного Launcher и совместимость с API модов.
`RPG_VERSION=0.1.1` — версия нашего выпуска; её сравнивает updater форка.
Интерфейс показывает `1.0.69 (RPG 0.1.1)`. Требования модов выше 1.0.69
по-прежнему отклоняются. В 0.1.0 общий VERSION ошибочно был 0.1.0, поэтому
проверки minLauncherVersion могли запрещать совместимые моды.

## Что изменено

- Имя EXE и папки: `EveJS-RPG-Launcher`; заголовок окна: EVEJS RPG LAUNCHER.
- Настройки, профили и логи: `%APPDATA%\EveJS-RPG-Launcher`.
- Начальные пути: `C:\projects\EveJS-RPG` и `C:\CCP\SandboxRPG-3396210\tq`.
- Native defaults: Game 27000, Image 27001, Proxy 27002, HTTPS/CDN 27003;
  Market HTTP 41110 / RPC 41111. Проверка состояния/готовности рынка,
  включая Start Stack и проверки внешних процессов, использует RPG-порты.
- Окружение очищается от унаследованных EVEJS_*, NODE_OPTIONS и NODE_PATH,
  как в RPG-Environment.cmd. EVEJS_PROXY_LOCAL_INTERCEPT=1 и
  EVEJS_PROXY_LOOPBACK_CDN_LISTEN_PORT=27003 передаются службам и инструментам.
  Выбранные в Launcher loader-моды по-прежнему передаются штатным способом.
- Клиент получает `/port:27000` и `/resfileserver=http://127.0.0.1:27002/resfiles/`.
  Если игровой порт/прокси изменён в Settings, аргументы используют выбранное значение.
- Проверка обновлений Launcher обращается только к форку klimesrenz и ищет
  `EveJS-RPG-Launcher.zip`. Автопроверка по умолчанию выключена. До первого
  релиза ручная проверка может сообщать об отсутствии доступа к релизу.

Это профиль для подготовленной native RPG-установки. Порты рынка и HTTPS
заданы в `src/rpg.py`; их изменение требует согласованного изменения сервера
и пересборки. Docker для этой сборки не проверялся. Конфигурация/мир сервера
не создаются и не переносятся. Sandbox RPG ZIP не является loader-модом:
его установкой и откатом раздел Mods не управляет.

## Запуск

1. Распаковать весь `EveJS-RPG-Launcher.zip` в отдельную папку. `_internal`
   должен оставаться рядом с EXE. Не заменять им обычный Launcher.
2. Для передачи управления остановить RPG Game и Market в их прежних
   консолях; сначала Game, затем Market. Закрыть RPG-клиент.
3. Открыть `EveJS-RPG-Launcher.exe`, проверить пути в Settings.
4. Start Stack запускает Market, затем Game. После готовности выбрать персонажа.
   Внешние процессы определяются как внешние; Launcher не присваивает их себе.
5. В исходном Launcher включён Hide test characters: GM-персонаж может быть
   скрыт. Настройка отображения не снимает GM-права. Права меняются отдельно
   через штатный ConfigEditor при остановленном RPG Game.

Проверить: основной Linux-туннель продолжает работать; RPG Market определён
на 41111; клиент входит в RPG-мир; ресурсы, чат и повторный запуск работают.
Для остановки использовать управление службами Launcher. При изменении
серверных/клиентских настроек перезапускать RPG-клиенты.

## Сборка Windows

Нужен Windows x64 и Python 3.12 в PATH. Запустить `Build-RPG.cmd`.
Он создаёт отдельную `.venv-rpg`, ставит закреплённые upstream build-зависимости,
запускает существующие проверки на временных данных и собирает PyInstaller.
Системный Python и игровой сервер не изменяются и не запускаются.
Результат: `dist\EveJS-RPG-Launcher.zip` и `.zip.sha256`.

GitHub Actions выполняет тот же сценарий после push ветки `rpg` или ручного
запуска workflow. Скачивать artifact `EveJS-RPG-Launcher-Windows`, внутри ZIP
лаунчера и SHA256. Workflow не публикует релиз автоматически. Для обновлений
нужен отдельный проверенный release с тегом `v0.1.x` и этим ZIP.

## Проверки и ограничения

Локальная Linux-проверка не заменяет Windows-сборку и игровой прогон.
Сценарий сборки проверяет конфигурацию, обновления, запуск клиента/служб,
native preflight и lifecycle на fixtures. Новые тесты не добавлены;
ожидания существующих тестов defaults/аргументов обновлены для RPG.

Архив содержит `RPG-BUILD.json` с commit, признаком dirty checkout и SHA256
файлов пакета. Исторические SOURCE-MANIFEST.json, BUILDING.md и
RELEASE-VALIDATION.md описывают upstream, а не приёмку RPG-версии.
После upstream merge заново проверять порты, APPDATA, окружение и updater.
